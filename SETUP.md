# Cuvori — turning on real accounts

Follow these steps once. About 20 minutes. Nothing here needs coding.

## Part 1 — Create the backend (Supabase)

1. Go to https://supabase.com and click **Start your project**. Sign up (GitHub login is easiest).
2. Click **New project**. Name: `Cuvori`. Choose a strong database password (save it somewhere, you will rarely need it). Region: **Frankfurt** (closest to Schwabach). Click **Create new project** and wait about a minute.
3. In the left menu click **SQL Editor** → **New query**. Open the file `supabase/schema.sql` from this repo, copy **everything**, paste it into the editor and click **Run**. You should see "Success". This creates the accounts table, the invite system and the security rules.
4. In the left menu click **Authentication** → **Providers** → **Email**. Turn **Confirm email OFF** for now (so people can sign in immediately without clicking an email link). Save. You can turn it back on later when you have a custom email sender.
5. In the left menu click **Project Settings** (gear icon) → **API**. Copy two values:
   - **Project URL** (looks like `https://abcdefgh.supabase.co`)
   - **anon public** key (a long text starting with `eyJ...`). This key is safe to put in the website — it only allows what the security rules allow.

## Part 2 — Put the keys into the site

Open `index.html` and find this line near the bottom (search for `CUVORI_CONFIG`):

```
window.CUVORI_CONFIG = { supabaseUrl: "", supabaseAnonKey: "" };
```

Paste the two values between the quotes, save, then commit and push in GitHub Desktop.
(Or paste the two values to Claude and it will do this for you.)

## Part 3 — Put the site online (Netlify)

1. Go to https://www.netlify.com and sign up with your GitHub account.
2. Click **Add new site** → **Import an existing project** → **GitHub**. Allow Netlify to see the `Cuvori` repository and pick it.
3. Leave the build settings as they are (the repo contains `netlify.toml`, which tells Netlify what to do). Click **Deploy**.
4. After a minute you get an address like `https://something-1234.netlify.app`. That is the real Cuvori. Every time you push to GitHub, Netlify updates the site automatically.
5. Later, to use **cuvori.io**: Netlify → **Domain management** → **Add a domain** and follow the instructions from your domain provider.
6. **If the page itself lives on GitHub Pages (cuvori.io does today)**, the payment functions still need Netlify. Deploy the repository to Netlify as above (only the functions matter there), then add one value to `window.CUVORI_CONFIG` in `index.html`: `functionsUrl: "https://main--cuvori.netlify.app"`. The page calls the functions there; they accept calls from `https://cuvori.io` (see `ALLOWED_ORIGINS` in `netlify/lib/cuvori.mjs` to add another address).

7. **Netlify: two branches, and credits (free plan: 300 a month).** Netlify's production branch is **`production`** (Netlify → **Project configuration** → **Developer settings** → **Branches and deploy contexts**); uploads go to **`main`**, which Netlify builds as free branch deploys. The page and Stripe's payment notices use the branch address (`main--cuvori.netlify.app`), so a fix works there as soon as it is uploaded. **The hourly job only runs on production**, so production must get the same payment code: on GitHub, merge `main` into `production`, but only when an upload changed the payment code (anything in `netlify/`, or `netlify.toml`), or after a changed value (below). **Production is kept on its 13 October code for now, by your decision of 29 October:** don't merge `main` into `production` until the payment code for the new prices is ready (Part 20, step 2 of "Turning the new prices on"). An upload of only the page, notes, tests or database scripts changes nothing the hourly job runs, and a production build is never skipped, so merging for it would spend 15 credits for nothing. ## Part 5 — Protected payments (Stripe escrow)

**Today's prices throughout this part:** the client pays the card fee and the payout fee on top (Part 13) and money is paid out 7 days after delivery. Under the new prices (Part 20, once switched on), Orders agreed from then on cost the client only the agreed price and are paid out 14 days after a valid delivery.

Money never touches Cuvori's bank account directly: Stripe holds it in Cuvori's Stripe balance until the client approves, Cuvori decides a dispute, or 7 days pass after delivery (14 days for Orders agreed under the new prices, Part 20). Until this part is done the site uses **direct payments** (the client pays the freelancer's IBAN/PayPal and both confirm in the Order, which says plainly that nothing is secured).

1. Create a Stripe account at https://stripe.com (country: Germany; individual is fine to start). Finish the identity and bank checks Stripe asks for.
2. Stripe dashboard → **Settings → Connect** → get started → choose **Express** accounts. Also set the platform name/branding ("Cuvori").
3. Stripe → **Developers → API keys**: copy the **Secret key** (starts with `sk_test_` in test mode, `sk_live_` later).
4. Stripe → **Developers** (bottom left) → **Webhooks** → **+ Add destination**. Choose **Your account** and the payload style **Snapshot**, not **Thin**: Cuvori reads only Snapshot events and refuses Thin ones, so with Thin no payment notice would ever be recorded. Keep the **API version** Stripe offers. Under **All events** tick these seven: `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `charge.refunded`, `charge.dispute.created`, `charge.dispute.funds_withdrawn`, `charge.dispute.closed`, `charge.refund.updated` (a refund that fails at Stripe afterwards; a destination made before this update gets it under **Edit destination** → **Select events**) → **Continue** → **Webhook endpoint** → **Continue** → **Endpoint URL** `https://main--cuvori.netlify.app/.netlify/functions/stripe-webhook` (the address the page uses, Part 15) → **Create destination**. How the money flows: client funds the Order price + the provider's processing cost → held → freelancer "Deliver for approval" (or submits a milestone) → client "Approve work & release €X" (or 7-day auto-release) → Stripe pays the freelancer's bank. ## Part 13 — The Order is the contract

There is no separate contract to draft, download or sign. In a chat either side presses **Order** and fills in the title, profession, scope of work, deliverables, deadline, revision rounds, the two sides' responsibilities, rights to the work and the price — optionally split into milestones. Once client and freelancer have accepted the same version, that Order is their agreement; the standard terms (cancellation, refunds, rights, disputes, law) are attached to every Order and shown before accepting. A printable copy exists, but it is a copy of the accepted Order, not a second agreement.

1. Run `supabase/schema_v18.sql` in the Supabase SQL editor (after v17). It adds the structured fields and explicit acceptance to the `contracts` table (the table keeps its old name; every row is an Order), plus `order_milestones`, `order_amendments`, `order_events` (append-only history — nothing there can be edited or deleted, not even by an admin), `order_payments` (the money ledger: every funding, release and refund) and `fee_schedules`.
2. **Acceptance.** Whoever creates or edits an Order has accepted that version; the other side presses **Accept Order**. Any edit before acceptance makes a new version and wipes the other side's acceptance. After acceptance nothing is silently editable: changes go through an **amendment** (extra money, new deadline, added scope or deliverables, extra revision rounds, a new milestone) that both sides accept; the original stays in the history. If an amendment adds money to a funded Order, the client is asked to fund the extra amount.
3. **Money.** Today, before funding, the client sees five lines: Order price, card fee, payout fee (Stripe), Cuvori fee (€0) and the total. (Under the new prices, Part 20, the client pays only the Order price: Cuvori pays the card fee and the payout fee itself (on small projects they cost more than its 5%, Part 20), and this screen changes with the payment code for the new prices.) The card fee is computed by `order_quote()` from the `fee_schedules` table — grossed up so the freelancer receives exactly the Order price — never from a number in the code. The payout fee (v50) is the table's **connect** row: Stripe bills Cuvori for paying freelancers out through their Express accounts (€2 a month for each freelancer account that gets a payout, plus 0.25% + €0.10 per payout, billed monthly in one sum), and Cuvori covers no fees, so the client pays it with the Order: the row's percentage of the price plus its fixed part, worked out before the card fee (the card's percentage applies to everything charged, so the card fee is taken on price + payout fee). A top-up (an agreed price increase paid later) pays the percentage only. The Order and its payment line keep it in their own field (`connect_cents`), never mixed into the card fee, so the card-fee refund (the surplus above the card's real cost, refunded right after payment) stays exactly as before; this fee is not refunded afterwards, and, like the card fee, it is not given back when an Order is cancelled — the price is; the page and Stripe's page both say so. A payment that arrives after its Order could no longer take it is not charged: Stripe's page only puts a hold on the card, and the hold is let go, so nothing is charged and nobody pays a fee. Only a payment that was already charged (rare: for example when test and live mode were switched while it came in) is refunded, the payout fee with it, except the card fee Stripe kept on it (Stripe does not give its fee back on a refund). If the client's bank then asks about the payment, Cuvori refunds the card fee too, so the refund is full (unless Stripe allows no more refunds on it). Switching the row off (Admin panel → Payment costs) makes the client pay no payout fee and leaves Stripe's bill with Cuvori. Check its numbers against Stripe's Connect pricing whenever Stripe changes its prices; the payment functions pause payments if the row ever asks for more than 2% + €5. Rows can be per region (EEA / non-EEA / any), country, consumer or business, and payment method; the most specific active row wins. Never set a card row's payer to **platform** to make Cuvori carry the card cost: the admin panel calls that choice "platform (Cuvori absorbs)", but today's payment code then pauses every payment until a client-paid card row is back (when it is the row that decides the checkout price, see below). It is only for pausing payments on purpose (Part 5, item 10; Part 7, item 2 says the same). Under the new prices Cuvori pays the card costs through the payment code for the new prices (Part 20), not through this table. Have a lawyer confirm that the client-paid card fee is allowed for European consumers before real money moves. Admin panel → **Payment costs** edits the table and shows a worked example. Since v53 it refuses to save a client-paid card row that decides the checkout price (region ANY, no country, any customer, method any/card) if that row would have collected less than Stripe really took on any payment settled in the last 12 months — the message names the payment and the amounts; no rate lives in the code. Rows that never decide the card fee at checkout (a country or region row, a consumer or business row, the payout-fee row), and rows set to platform or switched off (those pause payments instead), are saved as before. The freelancer's amount, the processing cost, the secured balance, releases and refunds are always kept apart. If Stripe bills Cuvori's fees "standalone" (it does for the whole account once funds segregation is switched on, and for some accounts anyway), a payment's record at Stripe shows a fee of 0, and the real fee is only in Stripe's Fees report, within 4 days. The payment code then never takes 0 as Stripe's fee: the card-fee refund and a late payment's refund wait until the hourly job has asked Stripe for that report and read the payment's fee in it, and Stripe's fee on the payment line stays empty until then. This needs the full secret key (`sk_…`); a restricted key would need read access to Stripe's reports and files.
4. **Milestones.** The client funds the whole amount up front; each milestone is submitted by the freelancer and approved with **Approve milestone & release €X**; the rest stays secured. A submitted milestone the client ignores is released automatically after the review window, like a whole delivery.
5. **Reports.** A progress report can be the delivery: the freelancer ticks "this is the delivery" (or picks the milestone it delivers). The client opens it from the chat or the bell and sees **Approve & release €X** or **Request changes** — a button that moves money always says so. Requesting changes through the report counts a revision round on the Order and stops the release clock inside the paid rounds.
6. **Cancellation and disputes.** Before funding either side can cancel. After funding the freelancer can cancel and refund everything still held; the client's route is a dispute, which stops every automatic release until you decide in Admin panel → Orders & disputes (release, refund or split of what is still held — money already released for approved milestones stays released). Card chargebacks and refunds made outside Cuvori also put the Order into dispute.
7. **Where things are.** Orders page: `#orders` (the old `#contracts` address still works). Code: the Order screens and their 7-language texts are inside `index.html` (`orders-ui.js` and `orders-i18n.js` are old copies the page does not load, which some tests still compare: change the screens in `index.html`), `netlify/functions/stripe-*.mjs` (`stripe-cancel.mjs` is new; `stripe-release.mjs` takes a `milestone_id`), `supabase/schema_v18.sql`. The site was never down — published sites stayed online — but new deploys were skipped until the next billing cycle. (Netlify's help page now says a team out of credits has all its projects paused, the payment functions included: Part 3, item 7.)

So the project is now wired like this: the Netlify **production branch is `production`**, a branch nothing is pushed to day to day, and **`main` is a branch deploy**. Every push to `main` therefore builds for free at **`main--cuvori.netlify.app`**, and that is the address `functionsUrl` points at. The page itself is not served by Netlify at all — cuvori.io is GitHub Pages — so Netlify only ever needs to carry the nine payment functions. A production deploy (15 credits) is needed only when the payment code or a value in Netlify changes, or after a pause (Part 3, items 7 and 8).

Two habits that follow: commit in batches rather than file by file, and remember that the Stripe webhook must point at whichever address is actually serving the functions: today that is `main--cuvori.netlify.app`, for testing and for live payments (Part 3, item 7), not the production address.


## Part 16 — Jobs a freelancer can trust (schema v20)

Run `supabase/schema_v20.sql` in the SQL editor (after v19). What it adds, in plain words:

- **Every job has a state**: active, filled, closed, expired, under review, removed. Active jobs expire after 30 days unless the owner renews them (the number is a setting, see below). The feed only ever shows active jobs; the owner sees all of theirs under **My jobs** on the Browse jobs page, with the reason whenever Cuvori stepped in and an “Ask for a review” button.
- **The card shows facts, not a score**: when it was posted, whether the client's identity is verified, whether the payment is secured (only when a protected-payment Order tied to the job was really funded by Stripe), how many hires the client has and their hire rate — or simply “New client”, which is not a warning. Freelancers can sort (newest, budget, deadline) and filter (identity verified only, payment secured only, posted within 24 h / 7 / 30 days).
- **Report job** on every job: one of seven reasons and an optional note. One report is a signal; three independent reporters move the job up your queue. Nobody is ever banned by a rule alone.
- **Limits that do not punish good clients**: a new client can post 3 jobs a day and keep 3 active; a verified one 10 a day and 15 active; the same job again within 7 days is refused with a plain sentence (“edit or renew that one instead”). All numbers are in Admin panel → Job review → Posting rules, including a switch to require identity verification before posting (off by default).
- **Risk check on the text**: fees before work, “write me on Telegram”, gift cards, passport copies, shortened links and the like add up to a score you never show anyone. At 5 or more the job is held for your review before it goes live and the owner is told so. A normal link (Drive, YouTube, a website) is never a problem; a shortener is only flagged.
- **Your review queue** (Admin panel → Job review): each job with why it was flagged, the client's history and verification, the reports and who sent them, and the actions taken before. Approve, false positive, hide, unhide, remove, warn (a message in their inbox) and suspend — every action lands in an append-only log with your reason. You can also mark a client verified after seeing proof (a video call with an ID); the note stays in the log.
- **Identity verification is provider-based**: a client is “verified” when Stripe has checked them (payouts enabled after Connect onboarding) or when a provider such as Stripe Identity says so — the table only keeps the state and the provider's reference, never a document. Stripe Identity itself is not wired yet; when you want it, it is one Netlify function that starts a verification session and one webhook event (`identity.verification_session.verified`) that writes `verified` into `identity_verifications`.
- **Paid posting later, no rewrite**: `posting_plans` holds free / limited / one-off / monthly plans and every profile points at one (`free` today). A plan can cap total posts or active posts; nothing in it can buy ranking. Your decision of October 2026: job posts stay free and there are no subscriptions (Part 20), so these plans stay unused unless you decide otherwise later.
- The hourly Netlify function (`stripe-auto-release`) also expires stale jobs. Without Netlify, expired jobs still never show in the feed (the read rule checks the date); only the stored state stays “open” until the sweep runs.

## Part 17 — When money goes wrong (schema v21): what Cuvori does on its own

Run `supabase/schema_v21.sql` after v20. The payment functions were rebuilt so that the awkward cases are handled without anyone touching the database:

- **The webhook never arrives** (Stripe gave up, a typo in the secret, Netlify was down): when the client comes back from the Stripe page, the site asks `stripe-confirm`, which looks the payment up at Stripe itself and funds the Order exactly as the webhook would. A paid Order can no longer sit unfunded.
- **The card money has not settled yet** when the client approves (banks take days): a release tied to its own card payment is allowed by Stripe straight away, so the normal case is instant. An Order paid in several parts (a top-up after an amendment) is paid from the balance instead; if that balance is still settling, the client sees “the payment provider is still settling… Cuvori retries every hour” and the hourly job finishes it. Nothing is stuck, nothing is paid twice.
- **The freelancer's Stripe account is not ready** (or closed) when money should go out: the release waits, the hourly job retries, and you can turn a release that has no transfer yet into a refund from Admin panel → Orders & disputes.
- **Retries never pay twice.** Every transfer, refund and reversal first looks at Stripe for one that already exists, and uses an idempotency key that is kept while the outcome is unknown and replaced after a definite failure (Stripe would otherwise replay the failure for 24 hours).
- **Top-ups** (an amendment made the Order more expensive): each payment is remembered with its card charge; refunds go back to the payments they came from, newest first; a top-up paid after the price grew again is kept and the rest is asked for, not refunded.
- **Chargebacks** (the client asks their bank for the money back) are kept apart from the Order's own dispute, which only the client or the freelancer opens and you decide. A chargeback is recorded on its own: the Order keeps its status, and a dispute either side opened keeps its reason; the client is flagged. While it is open nothing is paid out or refunded (not by an approval, a cancel, your decision or the hourly job), and the 14 (or 7) days stop. You answer it in the Stripe dashboard with the Order history, the delivery and the chat. If the bank sides with Cuvori, the Order goes on where it was: the days go on with the time they had left (a delivery made meanwhile gets its full days), the client can approve, the freelancer can deliver, and a payout or decision that was under way is finished by the hourly job as it was decided. If the bank sides with the client and nothing is left, the Order ends as refunded by the bank; if part is still held, that part goes on the same way, unless a payout or decision was under way for more than is left: then the Order comes to you to decide again (shown as a dispute that no side opened, so nobody is marked as having lost one). After the money was already released: Cuvori pulls it back from the freelancer's Stripe account so the chargeback is covered; won → the freelancer is paid again right away, also while the Order still holds money for its other parts (if their Stripe account is not ready, the hourly job pays it once it is), and a cancel or your decision never hands that money to the client: it divides only the rest; lost → the Order is marked refunded. If the freelancer's account cannot give it back, the Order is marked “needs a hand” for you. A payment back to the freelancer that Stripe made but whose answer was lost is counted before a cancel or your decision works out what the Order holds, so it is never handed to the client or paid twice; when two such saves fail at once (another payout's line as well), the Order's paid-out total is set to what Stripe's own record of its payouts shows. Stripe sends its notices out of order now and then: a chargeback the bank has already decided for Cuvori is never recorded as open when its late “opened” notice comes (Cuvori asks Stripe how it stands now). Two cases get a note on the Order, and nothing moves by itself: a chargeback the bank decided for the client and later turned round for Cuvori (“late win”: Stripe gives the money back to Cuvori's balance; decide by hand whose it is, then mark the note as handled), and a chargeback lost on a payment Cuvori had already given back in full (the bank may have taken it twice: check it in the Stripe dashboard under Disputes and ask Stripe for it back if so).
- **Two Checkout pages open** (two tabs, an old link): opening a new one retires the old one; if both were somehow paid, the second payment's card hold is let go, so the card is not charged twice, also while the first payment is still being recorded (one charged anyway is refunded, except the card fee Stripe kept on it).
- **A refund made in the Stripe dashboard** is mirrored into the Order (full refund → refunded; partial → dispute for you to decide). It is counted once, also when Stripe has to send its notice again; a part of it that had already been paid out to the freelancer (money that went out twice) gets a line of its own, and the Order's note says so, once, also when Cuvori's first try at the notice broke off and Stripe sent it again (a note you mark as handled doesn't come back with it). When the refund leaves the Order holding nothing, or comes while a payout or your decision is under way, Cuvori first counts every payout Stripe made for the Order that its books don't show yet (a payout whose answer was lost), so the note says what of the refund had already been paid out and the Order is finished as usual (check of 13 November: such an Order closed with nothing said, or stayed "releasing" or "resolving" for good). If the books can't take such a payout at all, the note "payouts not in the books" says what to check, and a payout or decision under way stops with a note that says so, never "try again".
- **The freelancer is paid, but the bank is slow**: after a release the money is in their Stripe account; Stripe pays it out to their bank on its own schedule — a few days, up to 7 for a brand-new account. The Order page tells both sides so.
- **Two chargebacks at once** (often the first payment and a price increase): the second one gets a note on the Order (“chargeback … also open on payment …”), and nothing on that Order is paid out or refunded while it is there. When the bank decides the first one, Cuvori takes the second one over by itself; if that breaks off half-way (the database did not answer), the hourly job, or Stripe's notice of the first one sent again, finishes it. Do not mark that note as handled while the bank is still deciding (once v56 has run, “Mark as handled” leaves that part of the note anyway).
- **The bank asks about a payment** (an inquiry): the Order is not released automatically until the inquiry ends. Stripe's notices can come late and out of order: what Stripe says about the inquiry now decides (one that has ended is not noted again; one the bank has already turned into a chargeback is handled as that chargeback at once). The client can still approve, and you can still decide. The note goes by itself when the inquiry ends; if Stripe's notice of that is lost, the hourly run asks Stripe and removes it. Before v56 runs, marking the inquiry's note as handled lets the automatic release go ahead again; once v56 has run, “Mark as handled” leaves that note.
- **A price increase both sides accepted is not paid**: the Order is not released automatically. The client pays the increase, or you decide the Order.
- **An Order in parts that holds nothing any more** (a chargeback the bank decided for the client took back the money for the parts left): it closes by itself, completed if anything was paid out. The parts not paid stay unpaid (their money went back to the client), and the Order's history names them. A part worth more than its Order still holds (money went back to the client, and no price increase is still to be paid) can't be paid out as it is: the client sees why instead of the Approve button, and the Order gets a note asking you to decide it; the note goes once the Order is decided or closed.
- **Stripe's fee on a payment still not known after 4 days** (today's prices; the card-fee surplus can't go back without it): the Order gets one note saying so. Check the payment in the Stripe dashboard, then mark the note as handled.
- **A decision that cannot finish** (you released to a freelancer who was banned later, or whose Stripe account was closed): you can pick another decision for that Order in the admin panel, as long as no money of the first one has moved at Stripe yet.
- **Your own Orders and Orders nobody disputed**: you cannot decide an Order on which you are the client or the freelancer; another admin has to. To decide an Order nobody has disputed, write a note to both sides (at least 10 characters).
- **What you look at before deciding** (once v56 has run): while a dispute or a decision is under way, a chargeback the bank has not decided yet is open, or the bank is asking about a payment (an inquiry), the admin panel's **Evidence** button shows the agreed text, the work handed in (the delivery and every part), the Order's history and the two sides' chat (the newest 500 messages). Every time you open it, it is written into the admin log. It is there only then (also while the bank's second chargeback on a payment is noted on the Order, and while an admin's decision is under way on an Order nobody disputed): not on other Orders (their chat stays private; a freelancer's own cancel that stopped is no dispute), nor once the dispute or the chargeback is decided (the chat is the two people's own again, also what they write later), nor on Orders where you are the client or the freelancer. The contract's dispute clause says Cuvori reviews the contract, the messages and the work and decides within 14 days, with its reasons to both sides; write those reasons in the decision's note.
- **Your decision is on record before any money moves**: the Order's history gets a "decision" line naming you, the decision, the amounts and your note, which nobody can change; your note goes to both sides in the chat, and the side that lost a dispute it was in is marked (never for a chargeback or a refund made in the Stripe dashboard). This also holds when Stripe stops half-way and the hourly job finishes the decision, and when the answer to saving the decision was lost and your second try (or the hourly job) carries it out: both sides are told once. If the database refuses the message or the mark at that moment, the hourly job tells it later (decisions of the last 7 days). A decision that replaces a stuck one says which one it replaced. Once v56 has run, each decision is also in the admin log (Part 20). If saving that history line fails, nothing moves: the hourly job leaves the decision alone and the Order's note asks you to decide again (the same decision is then carried out, or a different one replaces it; a 'split' at another percentage is a different one). “Mark as handled” does not remove that note: deciding again does, and so does the Order closing (for example a chargeback took all its money) or a chargeback sending it back to you as a dispute. The freelancer's own cancel that stopped at Stripe is finished by **Refund client** as it is: it is not your decision, so no decision line is written; the admin log says you finished it.
- **The hourly job and Netlify's 30 seconds**: Netlify stops a scheduled function after 30 seconds. The job stops starting new work in time (payouts after about 12 seconds, the rest by about 25), so it never stops half-way through a step; what is left waits for the next hour, oldest first. With many Orders due at once some are paid an hour or two later than their day.
- **An automatic payout waits for its own day**: the hourly job pays an Order or a part only if its review days are still over at the moment it starts the payout. If the client sent the work back and the freelancer delivered again while the job was working through its list, the new delivery's full days run first. Once v56 has run, the database refuses an automatic payout that starts early, too ("release_too_early").
- **Under the new prices (Part 20, once switched on):** a late payment goes back to the card in full, with Stripe's card fee (Cuvori carries it). A refund made in the Stripe dashboard after the freelancer was paid gets a line of its own, whole, and the Order counts only what it still held. After a chargeback Cuvori pulls back at most what the freelancer received from that payment (95% of it); the 5% stays booked, and the ledger check lists it under "to_decide". A lost chargeback's line says all the bank took, also when part of that payment had already gone back to the client (the bank can take the whole payment then, and the ledger check lists the part that went out twice); when Stripe gives that part back because the refund was proven (Stripe calls it "partially won", the chargeback still reads lost), the line says what Stripe kept. When the pull-back fails, the Order's note says what the freelancer kept (€95.00 of a €100 payout), not the 5% Cuvori kept, which was never with them. The hourly run adds any ledger line a step could not save, of every kind, from Stripe's record.
- **A refund Stripe can no longer make** (Stripe refunds a card payment only for a limited time): the answer and the Order's note say how much the client is still owed (and how much of that refund did go back to the card from a newer payment, such as a price increase). Pay the rest to them another way (a bank transfer). The Order then stays open with that note, and the hourly job asks Stripe again every hour: how such an Order is closed afterwards is not decided yet (tell Claude what you want). Stripe's exact answer for "too old" could not be checked here; check it once in Stripe's test mode.
- **A refund that failed at Stripe** (the client's card account closed): the Order counts the money as held again and its note says so. Refunding it again in the Stripe dashboard is counted as usual (at today's prices too), also when you do it before Cuvori has the "failed" notice, and also when the refund failed before the cancel or decision that made it was finished (its answer was lost: the Order then counts it as come back once that step is finished; check of 13 November). Before v56 runs the database can't record a failed refund: the note says it, the Order keeps counting the money as given back, and the refund you make again in its place is the same money (it is not counted a second time). Cuvori's own card-fee refund that fails is different: pay that to the client another way (a bank transfer), not with a refund in the Stripe dashboard, which Cuvori would count as a refund of the Order's money.
- **"Mark as handled"** (once v56 has run): on an Order where you are the client or the freelancer, another admin marks its note. When part of a note stays (the bank's inquiry or a second chargeback, which go by themselves once they are over, or a decision not on record), the answer says so.
- **A cancel or a decision while Stripe or the database doesn't answer** (or another payment step is moving the Order's money at that moment): nothing moves, and the person is asked to try again in a minute. Cuvori first counts every payout Stripe made for the Order, so what the cancel or the decision records is what really moves. If the books can't take a payout Stripe made (paid out and given back would be more than was paid in, for example after a refund in the Stripe dashboard), the person is told the Order is under review, you see why, and the Order's note ("payouts not in the books") says what to check in the Stripe dashboard. The note stays until you mark it as handled, also when the books can take those payouts later (for example when the refund made in the Stripe dashboard failed): the books fitting doesn't show that money didn't go out twice, so check it in the Stripe dashboard first. Another payment step working on the Order at the same moment (a refund made in the Stripe dashboard, a refund that failed at Stripe, the bank's decision on a chargeback) never writes over it: it adds its own note to the notes there as they are when it writes, and a note you marked as handled in that moment doesn't come back (check of 12 November, fourth part; before, such a step could wipe the note out). If the note itself can't be saved at that moment, the person is asked to try again in a minute.
- **A chargeback on such an Order** is handled all the same, and the same note tells you what could not be counted. What is pulled back from the freelancer for it is written down on the Order (its line names the chargeback) and pulled back once, however often the bank's notice comes; when the books still can't take the payout after it, the Order's paid-out total stays as it is (at both prices; at the new prices the bank's first notice then failed once before Stripe's next send went through: fixed in the check of 12 November, fifth part). If the bank then decides for the client, the Order says when Cuvori covered part of what the bank took: "chargeback lost; … could not be pulled back from the freelancer" is what Stripe refused to pull back from them (their Stripe balance empty); "chargeback lost; Cuvori covered … the Order no longer had it" means the freelancer gave back all they had to and the money went out twice before, so don't try to pull anything more back from them (worked out from Stripe's record when the books are missing the payout, so it is said also when nothing was pulled back from them). Check it in the Stripe dashboard. When the bank decides a chargeback for Cuvori, everything pulled back from the freelancer for it is paid back to them right away, worked out from Stripe's own records (only the chargeback's own pull-backs, never one you made by hand). What the Order no longer has for it (money went out twice) Cuvori pays from its own money (your decision of 12 November), and the Order's note says how much ("re-payment covered by Cuvori after chargeback …: Cuvori pays … owed back to the freelancer from its own money"; written before the money moves, so it reads the same while the re-payment still waits, say for a freelancer who is banned or whose Stripe account can't take money yet, and the note "chargeback won …" says it waits): check the Order's payouts and refunds in the Stripe dashboard, then mark it as handled. Nothing more is paid if the money comes back to the Order later (a refund made in the dashboard that fails, say). If Stripe or the database doesn't answer for a moment while a bank's notice is handled (or while one of these notes is written), the notice fails and Stripe sends it again (it tries for up to 3 days), so nothing is decided on books that are missing a payout, and no note is left out.
- **A chargeback on a later payment of an Order** (a top-up, a price increase), at both prices: what is pulled back from the freelancer for it is never more than they were paid out of that payment, that is, by the payouts made after it came in (your decision of 12 November). A chargeback on a top-up for a part not paid out yet takes nothing from them: on an ordinary Order the bank takes it from the money the Order still holds for that part, and Cuvori loses nothing. Only on an Order where money went out twice before does the Order hold too little for it; then what the bank takes is Cuvori's loss, and the Order's note says how much ("chargeback lost; Cuvori covered …").
- **A part whose payout was counted while its "paid out" mark could not be saved**: the hourly job marks it, with its history line and chat card.
- **Decisions told to both sides** (the written reason in their chat, and the "lost a dispute" mark): once, by the step that carries the decision out (your decision itself, before the money moves, or your second try or the hourly job); the hourly job's catch-up tells only decisions that were carried out, so one you replace before that is never told. When you replace a decision that was told but could not be carried out (the freelancer could not be paid), the mark it put on the other side is taken back. Decisions made before this update are never told again.
- **A part approved at the moment a dispute is opened** (once v56 has run, at any prices): the client is told there is nothing to release, and nothing is paid out.

Everything on the list is covered by `tests/attack-money.mjs` (60 checks against a fake Stripe that enforces Stripe's real rules) and `tests/attack-functions.mjs`.

## Part 18 — The professions, and how to add one

Cuvori knows 31 professions in six groups: video & media (video editor, videographer, photographer, motion designer, animator, colorist, drone operator), audio & music (sound designer, audio editor, voice-over artist, music producer), design & visual (graphic, brand & logo, UI/UX, illustrator, 3D artist, presentation designer, photo retoucher), writing & content (copywriter, content writer, scriptwriter, translator, proofreader & editor), marketing & social media (social media manager, paid ads, SEO, UGC creator) and development & technology (web, mobile app, no-code website builder — plus game developer, which is deliberately still closed so you can see what a closed one looks like in the admin panel).

Each profession owns its own lists: what kind of work it does, the skills it is asked for and the software it works in. On **Post a job** the client types a word — "logo", "vestuvės", "tłumacz", "монтаж", the name of a whole group, even something only that trade's own list mentions, such as "wedding" or "thumbnail" — picks one profession, and only then do that trade's chips appear. Nothing is preselected, and a job cannot be published without a profession. The freelancer side uses the same lists for the profile and the search filters, so a client's filter and a freelancer's profile can never drift apart.

Everything lives in one file: `professions/seed.js`. To add or change a profession, edit that file, then run `node tools/gen-professions.js`, which rewrites `supabase/professions_seed.sql` (for the database) and `professions/config.json` (the copy inlined in `index.html` as the offline fallback — paste it over `window.CUVORI_PROFESSIONS`, then rerun `python3 tools/csp.py index.html`). Labels for new options go in English in the seed; the six translations go in `professions/tr-<lang>.json` under `options`, and the generator merges them. A missing translation falls back to English rather than breaking.

Two things the seed deliberately never overwrites on a re-run: **active** (open for joining) and **sort_order**. Once a profession is live, the admin panel owns those — so after seeding new professions, check Admin panel → Professions, and open or close what you want. The same is true of filter options once you have edited them by hand in the admin panel (`filters.admin_edited`).

A new key or secret in Netlify only reaches the running code once the functions are built again: see Part 3, item 8.

## Part 19 — Reviews

A review belongs to an Order. Nobody can review a person they never worked with on Cuvori: the database only accepts a review from the two people named on an Order, once that Order is **completed**, and only one review per side. Both sides build a reputation — the client reviews the freelancer and the freelancer reviews the client.

**One rating.** Stars from 1 to 5, nothing else: no separate marks for quality, communication or delivery. A profile reads `4.8 ★ · 37 reviews` and nothing more. Four or five stars may be left without a word. One, two or three stars must say why: a reason from a short list, plus a written explanation of at least ten characters, both enforced in the database, not only in the page. The client's list is poor quality, missed deadline, poor communication, did not follow agreed scope, unprofessional behaviour, other. The freelancer's list is poor communication, repeatedly changed agreed scope, payment or dispute issue, unreasonable demands, did not provide required materials, abusive behaviour, other. "Did not follow agreed scope" is for something in the agreed Order that was not delivered — the form says so under the choice — and not for refusing extra work that was never part of it.

**Blind, so nobody answers a bad review with a bad review.** Your review is hidden until the other side has reviewed too, or until the review window runs out; then whatever exists becomes public. Before that moment you may correct your own review twice; once it is public it is locked for both of you. The window is a setting, not a number in the code: it is `review_window_days` in the site settings table (14 days out of the box; not the 14 days before an Order is paid out, Part 20). Change it in the Supabase SQL editor with `insert into public.site_settings (key, value) values ('review_window_days', '21'::jsonb) on conflict (key) do update set value = excluded.value, updated_at = now() returning key, value;` (21 days in this example; Supabase must show one row, **review_window_days | 21**). A changed window applies at once to Orders that have no review yet, and to the second side of an Order where only one side has reviewed; a review already written keeps its own deadline. Or change it from the admin panel once the settings screen carries it. Existing reviews keep the deadline they were written under.

**What people see.** The moment an Order is completed, both sides get a card in the chat and a line in the bell: *How was it working with …?* — it opens that Order, where the review button is. A public profile shows the average, the number of reviews, and the reviews themselves, each marked **Verified Cuvori Order**. That badge cannot be given by hand; it is what having an Order means. Reviews never show a price, a file, a message or anything else private about the Order.

**Moderation.** Anyone can report a review they can see (Admin panel → Reports). Admin panel → Reviews lists every review with its state and lets you hide or unhide one. Hiding takes it out of the public list and out of the average immediately, keeps the text exactly as the person wrote it, and records who hid it and why in the moderation log. Nothing is deleted and no review is rewritten. Deleting an account removes the reviews that person wrote and received, the same way the rest of their data goes.

The rating is always counted from the reviews that are visible at that moment, so hiding one changes the number straight away and there is no stored total that can drift.

**Where it lives.** `supabase/schema_v22.sql` (table `order_reviews`, the rules, the RPCs, the moderation), the review flow inside `index.html`, `tests/reviews.js` (37 browser checks) and the review section of `tests/db/30_attacks.sql` (26 database checks). The older profile-to-profile table `public.reviews` from v3 is untouched and its rows are kept, but it no longer feeds the public rating.

## Part 20 — The new prices in the database (schema v56, switched off)

`supabase/schema_v56.sql` puts your final pricing decisions into the database: **clients pay only the agreed price** (no client fee, no subscription; job posts and matching help are free), **freelancers pay 5% commission** on projects paid through Cuvori, kept from every amount paid out to them, top-ups included (€100 paid out: €5 kept, €95 sent), **Cuvori pays the card costs**, and **14 days** to review a delivery before the money is paid out automatically (each Order's own `auto_days`; the reviews' `review_window_days` in Part 19 is a different setting and does not change it). **The new prices are switched off.** Running v56 changes no Order and no payment line that exists, and every new Order keeps today's prices (plan 1: no commission, the client pays the card fee and the payout fee on top, 7 days) until you turn the switch. Three of its rules do apply from the moment v56 runs, also with the switch off: on every Order paid through Cuvori, nothing is paid out for a part while the Order is in dispute or a chargeback is open; on every Order, a ledger line's Order, kind, amounts, status and Stripe reference can no longer be changed (Stripe's fee and the card-fee refund can still be added, as today); and an Order agreed after v56 can no longer be set back to a proposal. Since the payment audit of 31 October, more rules apply at once, at any prices. All amounts are whole cents. **Rounding:** the commission is rounded half up to the cent (0.5 cent and more goes up), and over several payouts it is taken on the running total, so the whole is 5% of everything paid out, to the cent. `pricing_next_commission` gives the payment code the amount for the next payout. With the payment code working right, only payout lines added afterwards from Stripe's record (`release_late`, when a line was lost and the books are put right) can leave a difference: up to a cent for each such line. One more case: a payout always leaves the freelancer at least a cent (Stripe can't send €0), so a payout of 1 cent keeps nothing; when an Order's last payout is such a 1-cent part and its 5% would have taken a cent there, the Order keeps 1 cent less than 5% (parts of €2.09 and €0.01: €0.10 kept, 5% of €2.10 is €0.11). The ledger check lists every difference, also one a mistake in the payment code would leave (the database records such a payout as it happened). Stripe's monthly Connect fees (€2 per active account, the payout fees) are billed by Stripe for the whole month and are not split per Order.

**The rules the database enforces:**

- An Order records its prices when it is proposed. Once both sides accept, nobody can change them with a normal change: not the payment functions, not the admin, not you in the SQL editor. Under plan 2 that includes its 14 days and the way the Order is paid (through Cuvori or directly). An Order agreed after v56 can also never be set back to a proposal.
- A proposal sent or changed from the page of this update names the plan its form showed: if the switch moved in between, nothing is written (`pricing_changed`, through `order_create_at_prices` and `order_update_at_prices`), and the page shows the prices in force before the person sends again. An Order paid directly doesn't depend on the prices and is not checked.
- If the switch moved while an Order was still a proposal, Accept answers "order_changed". The Order then has the prices in force (the Order screen shows their days; their 5% only from step 1 of "Turning the new prices on"), and both sides read and accept it again. If it is below the €2 minimum, Accept answers "bad_price" until the price is changed.
- Under plan 2, an Order paid through Cuvori can't be made, given a lower price (by a change or an amendment) or accepted below €2. A proposal from today's prices that a change takes to plan 2 keeps its price until then: Accept answers "bad_price" until it is €2 or more. The €0.50 rule for top-ups stays as it is.
- Under plan 2 the client pays the agreed price and nothing on top, and every payout keeps 5%. The ledger holds the truth about the money: a ledger line is written after its money has moved at Stripe, so the database never refuses a line because of its amounts. A refusal could not bring the money back; it would only hide it. It refuses only a **badly written** line, which the payment code would write wrongly every time and which testing finds: a line not marked `succeeded` or not from Stripe, no entry key (every line has its own, never used twice), not exactly one Stripe id (one line per payment, payout, refund, pull-back and chargeback; a list of ids would let a refund be counted twice), or the id of another kind of Stripe object than the line's (a payment `pi_…`, a payout `tr_…`, a refund `re_…` or `pyr_…`, a pull-back `trr_…`, a chargeback `dp_…` or `du_…`: a payout naming its payment would pass once and be refused at the second payout from that payment, after Stripe had paid it), a payout that doesn't say what it kept and what it sent (sent = paid out minus kept), or keeps below 0 or more than its amount, a re-payment after a won chargeback whose line doesn't read `chargeback_won <dispute id>`, or a pull-back whose line doesn't read `chargeback <dispute id>` (as today's code writes it; the ledger check finds each dispute's pull-backs by it), or a card-fee refund that is more than the payment's fee, has no Stripe refund id of its own, or is on any other line than its payment's. Each Stripe payment, payout, refund and chargeback can be written only once. **Everything else is recorded as it happened, and the ledger check lists the Order for you** (see Reading): a payment above the agreed price, a payment that charged the client card costs, a payout that didn't keep exactly 5% of the running total, more paid out than came in (for example a refund made in the Stripe dashboard after the freelancer was paid), a re-payment without a won chargeback or above what it pulled back, and money the Order counts but whose line was never written.
- **The 14 days start with a valid delivery.** Under plan 2, on an Order paid through Cuvori, a delivery, or a part handed in, needs a link to the work (the page asks for it, and the database refuses a delivery without one). Asking for changes within the paid rounds stops the clock; the next delivery gets a full 14 days again.
- **A dispute stops payouts.** Opening a dispute stops the clock (as before). On every Order paid through Cuvori, nothing is now paid out for a part while the Order is in dispute (or no longer being worked on) or the bank has a chargeback open; a payout that had already begun before the dispute is still recorded. Your decision on a dispute goes through as before: pay out, refund, or divide. 5% is kept only on what the freelancer is paid.
- No ledger line, also none from before v56, can be moved to another Order or have its kind, amounts, card fee, status or Stripe reference changed afterwards. The payment code never did that: it only adds Stripe's real fee and the card-fee refund to a line, and that still works. A refund that fails at Stripe after its line was written gets a line of its own, at any prices (kind `refund_failed`, naming the failed refund `re_…` or `pyr_…`, for the money that came back): the ledger check, the money summary and the commission report count refunds minus failed refunds.
- The Order's commission total is kept by the database from the ledger lines, never written by hand. A plan 2 line can no longer be changed: only Stripe's real fee and the charge id are written in once, and the refund of a card fee charged by mistake once (at most that fee, with the refund's own Stripe id).
- Payment code that does not know plan 2 cannot move money on a plan 2 Order. This covers the 13 October hourly job on Netlify production, and today's code. It is stopped when it takes the Order's lock or a money key, which it does before it moves an Order's money at Stripe (two refunds in today's code take a key that names the payment instead: the card-fee refund, and the refund after the client's bank asks about a late payment; neither can happen on a plan 2 Order, because today's code can never take a plan 2 payment), and at every write. That also stops it from charging or letting go of a card hold when a payment page is paid, or sending back a late payment, on a plan 2 Order: those steps wait until the new code is live, which is why the new code goes live before the switch (steps 1 and 2 of "Turning the new prices on", below). A cancel or a dispute decision on such an Order can still let go of a card hold that is waiting: nothing is charged, and the client pays again later. Plan 1 Orders work exactly as before, and so do people's own steps that move no money (deliver, ask for changes, open a dispute). Approving a plan 2 Order paid through Cuvori, or a part of it, pays money out, so it is refused until the new code is live (the client sees an error and can approve again then). The new payment code identifies itself by sending the header `x-cuvori-pricing: 2` with its database requests; an Order accepts money steps only from code that knows its plan.
- The price plans, the switch and its log can only be changed by you, here in Supabase. Visitors and members can read the plans and which plan is on, but not your note on the switch. Only an admin can read the switch log (with every note).

- `select public.admin_pricing_check();` checks every plan 2 Order. It should show `"problems": []`; ask for help with each Order it lists. Under `"problems"` it lists:
    - `commission_off`: the commission kept is not 5% of what was paid out (with the payment code working right, a difference can only come from payout lines added afterwards, up to a cent for each, or from a last payout of 1 cent, see Rounding; a re-payment that kept something again shows here too);

    - `paid_more_than_agreed`: more was paid in than the agreed price (counting what stayed after refunds and chargebacks);
    - `client_charged_card_fee`: a payment charged the client card costs, which Cuvori pays under the new prices, and they were not refunded (it stops being listed once the payment code writes that refund, all of it, on the payment's line; a part refunded leaves the rest listed).     - `more_out_than_in`: more went out in refunds, chargebacks and payouts than came in: money went out twice;
    - `commission_without_money`: more commission is booked than the money Cuvori still has from the Order (for example a small refund made in the Stripe dashboard after the payout; a bigger one is listed as `more_out_than_in`);
    - `repay_off`: a re-payment after a chargeback without a won chargeback, or more than that chargeback pulled back;
    - `commission_twice`: normal payouts add up to more than was paid in, so 5% was kept on money paid out twice, for example money pulled back after a chargeback that went out again as a normal payout instead of a re-payment;
    - `chargeback_not_recorded`: a chargeback was lost, but its ledger lines show less than the bank took (today's code writes only what Cuvori still held, for example when the pull-back from the freelancer failed; the payment code for the new prices writes what the bank took in full, also when part of the payment had already been refunded): Cuvori lost the rest, which the Order's note also says;
    - `money_left_at_cuvori`: a finished Order left Cuvori with more than its commission, for example a divided dispute decision that took the 5% out of the client's refund instead of the freelancer's share (not listed while a chargeback is open or the Order notes a won one's re-payment as still owed, which the hourly run pays, nor when `line_missing` already lists it);
    - `line_missing`: the Order counts more money paid in, paid out or refunded than its lines show. A line was not written; the payment code for the new prices is to add it from Stripe's record in its hourly run (step 1 of "Turning the new prices on"; today's code does that only for some kinds of lines), so ask for help only if it is still listed the next day.

  Under `"to_decide"` it lists `commission_on_lost_chargeback`: a chargeback lost after the payout, where the freelancer's money was pulled back but the 5% is still booked as commission (with the 5% on the lost part; your decision, below); and `commission_on_pulled_back_payout`: a payout pulled back after a chargeback that was not lost, and not paid back as a re-payment, so the 5% kept on it is still booked although the freelancer kept nothing of it, whether that money then went back to the client or out again as a normal payout (then the 5% was kept twice, and `commission_twice` may list it too; the same decision).

  What the check can't see or record: For `chargeback_not_recorded` only the Order's latest chargeback is checked (a new chargeback replaces the Order's record of the earlier one); the other items read each chargeback's own lines. ## Part 22 — Funds segregation at Stripe (prepared, switched off; to be turned on after launch)

**Owner's decision (2 November 2026): this is a must-do, not an option.** Cuvori will run with funds segregation. It is switched on after the new prices are live, in the five steps below and in that order; nothing in them can be skipped, because each one protects real money. Until then nothing about it is live, and the site does not mention it. The first step towards it that needs you is the message to Stripe (step 2); ask Claude for the draft when you are ready.

**What it is. Stripe can keep each client payment "held apart" on Cuvori's Stripe account, tied to that one payment, until it is paid out to the freelancer or given back. Money held apart is not in Cuvori's balance: Cuvori's own payouts, Stripe's fees and refunds or chargebacks of other Orders cannot use it. Stripe calls it "funds segregation" (allocated funds). It is a private preview: Stripe must invite Cuvori's account first. Nothing in this update asks Stripe for it, and Cuvori does not have it.

**What is ready, and switched off.** The payment code has it behind one Netlify setting, `STRIPE_FUNDS_SEGREGATION`. It does nothing unless the setting is exactly `on`. When it is on, for Orders under the new prices only:

- the payment page asks Stripe to hold the payment apart, and takes only Visa, Mastercard and American Express cards (Stripe holds apart only these and Discover; the page can block Diners, JCB, UnionPay and Elo only together with Discover);
- every payout is linked to the payment it comes from (an Order with a top-up is paid in two parts, one per payment), and Stripe moves the 5% to Cuvori's balance with each payout;
- refunds and chargebacks come out of the payment's own money first;
- the hourly job moves to Cuvori's balance what a closed Order still has held apart (money pulled back from a freelancer after a lost chargeback). If Stripe will not move it, the Order's note asks you to write to Stripe; the note goes once nothing is held apart any more. It never moves the money of an Order that still owes the freelancer (a won chargeback's re-payment not made yet) or still holds money (a refund that failed at Stripe).

Orders paid before, Orders at today's prices and Orders paid directly work exactly as now. Turning the setting off again changes nothing for payments already held apart: their payouts stay linked to them.

**Never turn it on, and never accept Stripe's invitation, before all of these, in this order:**

1. **The pricing-v2 code is live on cuvori.io and in Netlify production** (Part 20, step 5, and "Turning the new prices on", step 2). Stripe's own guide says that once funds segregation is on, Stripe bills **all** fees of the whole account later ("standalone fees"), also for payments that are not held apart. The code on `main` today (13 October) reads such a payment's fee as 0: it would send each client their whole card fee back, and record Cuvori's card cost as 0 (tested: `tests/attack-funds-segregation.mjs`, F3, against that code). 3. **Cuvori's own Stripe balance has a cushion.** With everything held apart, Stripe's fees, chargeback fees and refunds beyond a payment's own money come out of Cuvori's own balance, while the 5% only arrives with each payout (up to 14 days later).
